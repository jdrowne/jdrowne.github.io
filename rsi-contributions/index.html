Background

"Self-improvement" can mean changing three different things. Each level goes deeper than the one before. Most confusion so far came from mixing them up.

1

The harness

Working today

The instructions, tools and workflow wrapped around a model. HGM works at this level. Gains are real but capped by how good the model is.

2

The model's weights

Early results, last month

The billions of learned numbers that make up the model itself. Two recent projects changed weights using AI: one by editing them directly, one by having the model train itself.

3

The improvement process

Not shown yet

The loop rewrites its own rules for what counts as progress and how to look for it. Mostly theory. HGM's rules, for example, are written by people and stay fixed.

The tracks below match these levels. Track A works on level 1, Track B on level 2, and Track C checks whether an improvement at any level is real.

First steps

If you only do three things next, do these. Each one starts a track.

  1. Track A: Send the HGM bug report.Claude drafts it with the one-line fix. You review and submit it. About an hour.
  2. Track B: Reproduce the weight-editing result and run one cheap control.The edited model and logs are public. Runs on an ordinary computer, slowly. A few days.
  3. Track C: Write a one-page "is this improvement real?" checklist.Use it on steps 1 and 2 before believing any result, including the author's.

Track A: Improve HGM

Harnesses are powerful. In the HGM paper, an evolved harness took the same model (GPT-5-mini) from 53.2% to 61.4% on the coding problems it was tuned on, and from 34.8% to 40.1% on new problems it had never seen.

What the author found

  • The paper's wins over other methods come down to 1 or 2 problems, from one run of each method. That could easily be luck.
  • The current public code has a bug. It overwrites each version's own scores with its descendants' scores, and those records keep growing until the program would likely run out of memory. The fix is one line.
  • The first public version, with its default settings, doesn't do what the paper describes. It ends up choosing versions by their own score, the very method the paper argues against.
  • In a simulation, most of HGM's benefit came from testing each version a few problems at a time and dropping weak ones early. The headline idea, judging a version by its descendants, helped clearly in only 1 of 6 test worlds.

Steps

Needs: an AI API key or a self-hosted open model, Docker, and a budget for AI usage. The HGM authors spent about $5,000 on all of their experiments combined.

Track B: Let AI improve model weights

You were right that this can be cheap. Two results from the last month show two different routes.

Weight-space programming

Route 1: direct editing · MIT CSAIL, 2 Nov 2026

A frontier model (the post calls it GPT-6 Astra) read the weights of a small open model, Qwen3.5-0.8B, and edited them directly. No training and no GPU. It changed 0.016% of the weights after 50 practice runs.

MATH-5007.9% → 48.1%
GSM8K13.8% → 67.1%
IFEval21.0% → 62.3%

Scored on benchmarks the editor never saw. Most of the gain came from stopping the model from looping: answers stuck at the length limit fell from 93% to 33%. On a second model, Gemma 3 270M, it couldn't improve anything. The post's authors call these very early results.

Terminal-RSI

Route 2: self-training · arXiv 2610.22192, Oct 2026

A 27-billion-parameter open model (Qwen3.8-27B) turns its own verified successes into training data, then trains itself with reinforcement learning, in repeated rounds.

Terminal-Bench 2.151.7% → 86.5%
Terminal-Bench 4.00.0% → 19.8%

This is real training, which for a model this size likely needs a multi-GPU server (an estimate; the page doesn't say). The page also doesn't say whether training tasks were kept separate from test tasks.

What this means

Direct editing is cheap and new. Self-training works but costs more. Neither one is yet a model improving itself: in the first, a large model edits a different, much smaller one.

Steps

Needs: a computer that can run a 0.8B model (a recent Mac can, though long math answers are slow), plus the public logs and model.

Track C: Make sure improvements are real

Every self-improving system grades itself against tests. When it's pushed hard, it finds ways to score higher without getting better. Tracks A and B both need a grader that can't be fooled.

What the author found

  • In the simulation, the winning version's score on the tests it was chosen with overstated its true quality by 4 to 7 points.
  • One run per method can't tell methods apart. Even when one method was truly 5 to 9 points better, it won a single head-to-head only 60% to 74% of the time.
  • The system HGM builds on, the Darwin Gödel Machine, was caught gaming its own checks.
  • Terminal-RSI doesn't say whether its test tasks were kept separate from training.

Steps

Needs: mostly time and care. Very little computing.

Ground rules

These make results believable. They also keep a self-improving loop something you can inspect. Claude will help with all three tracks on these terms.

  • Keep test problems out of reach of the system being improved.
  • A person approves each change that gets kept, especially changes to weights.
  • Log every change so it can be reviewed and undone.
  • Run model-written code in a sandbox. HGM's own README warns about this.

Details behind the findings

The HGM paper: what holds up

Paper's claimWhat the author found
HGM beats the Darwin Gödel Machine, 56.7% vs 53.3%True as reported, but that is 34 vs 32 problems out of 60, from one run each.
Uses fewer computer hoursPlausible. Most likely from running tests in parallel and stopping early, not from the headline idea.
Its estimate predicts which versions will have good descendants (0.778 vs 0.285)The simulation produced the same gap in a world where that kind of potential doesn't exist, so this test can't show it.
61.4% on full SWE-bench VerifiedMeasured on the same problems it was tuned on, so inflated. On new problems: 34.8% → 40.1%.
Human-level on SWE-bench LiteTies the best human-built agent, within 1 problem either way.
Approximates the optimal "Gödel Machine"Only in a narrow theoretical setup. The practical version estimates something different.

The HGM code

current (013872d)tree.py returns a node's own results list and then appends to it, so each expansion overwrites that node's scores with its descendants' and the lists keep growing. Introduced by a cleanup commit on 24 Nov 2025, after the paper.

The simulation

Six made-up worlds, from "a version's descendant potential doesn't exist" to "strong hidden potential." Each world was run 400 times with the same budget as the paper. It's a simplified model, so treat the numbers as direction, not proof.

Glossary

Harness
The program around an AI model: its instructions, tools and step-by-step workflow.
Weights
The learned numbers inside a model. Changing them changes the model itself.
Open-weight model
A model whose weights are published, so anyone can download, run and change it.
HGM
Huxley–Gödel Machine. A method for deciding which version of a self-editing coding agent to improve next.
Benchmark
A fixed set of test problems used to score models, such as SWE-bench (fixing real code bugs) or MATH-500.
Held-out test
Problems kept away from the system during improvement, so a score on them shows real ability rather than memorization.
Fine-tuning / RL
Ways of training a model further. Reinforcement learning (RL) trains on trial and reward.
Gaming a test
Raising a score without getting better, for example by exploiting a flaw in how answers are checked.
