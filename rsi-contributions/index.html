Background

RSI (recursive self-improvement) means AI improving itself. This page lists small open-source contributions that could advance it. AI can improve two things:

  • The harness: the instructions, tools and workflow around a model. Track A works here.
  • The weights: the learned numbers that make up the model itself. Track B works here.

Track C checks that improvements at either level are real.

Tracks

Track A: Improve HGM

HGM (Huxley–Gödel Machine) is an open-source system in which an AI repeatedly rewrites its own coding harness.

Findings

  • The current code has a bug that corrupts each version's scores and can exhaust memory. The fix is one line.
  • The paper's wins over other methods come down to 1 or 2 problems from single runs, which could be luck.
  • In a simplified simulation, most of HGM's benefit came from testing each version a few problems at a time. The paper's main idea, judging a version by its descendants, helped in only 1 of 6 scenarios.

Steps

  • Report the bug and fix to the HGM authors. It is filed on a fork but not yet sent to them.
  • Compare judging by descendants against judging by own score, with several runs of each.
  • Try testing a few problems at a time in OpenEvolve, a similar open-source tool.
  • Publish every record from one full run, so others can compare methods without rerunning it.

Needs: AI model access, Docker to sandbox the AI-written code, and a budget. The HGM authors spent about $5,000 in total.

Track B: Let AI improve model weights

Findings

Two recent results show this can be cheap:

  • Weight-space programming (MIT CSAIL, November 2026): a frontier AI directly edited 0.016% of the weights of a small open model, Qwen3.5-0.8B, with no training and no GPU. Its score on unseen math problems rose from 7.9% to 48.1%, mostly because the model stopped repeating itself. The same approach failed on a second model.
  • Terminal-RSI (October 2026): a 27-billion-parameter open model trained itself on its own verified successes. Its score on a test of command-line tasks rose from 51.7% to 86.5%. This needs real training hardware, and the paper doesn't say whether test tasks were kept out of training.

Steps

  • Reproduce the editing result. The edited model and logs are public, and it runs on an ordinary computer.
  • Check whether a setting that discourages repetition gives the same gain without editing any weights.
  • Try the method on another model and another skill.
  • Then have a model edit a copy of itself, once Track C is in place. A person approves each change it keeps, and every change is logged so it can be undone.

Track C: Check that improvements are real

Self-improving systems grade themselves. Under pressure, they find ways to raise their scores without getting better. The Darwin Gödel Machine, which HGM builds on, was caught doing this.

Findings from the simulation

  • The winning version's score overstated its true quality by 4 to 7 points.
  • A single run can't tell methods apart. A method truly 5 to 9 points better won only 60% to 74% of single head-to-head runs.

Steps

  • Write a one-page checklist: hidden test problems, repeated runs, a simple baseline to beat, and a grader the system can't change.
  • Apply it to Tracks A and B.
  • Turn it into a small open-source tool that works with HGM, the Darwin Gödel Machine and OpenEvolve.
